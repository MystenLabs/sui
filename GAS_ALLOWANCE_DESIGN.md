# Gas-only spending allowances

## Scope and threat model

A funder escrows a bounded SUI balance for one designated spender. Subsequent transactions require the spender's signature, not the funder's signature or spender-owned gas coins. The spender can consume the escrow only through native gas settlement. A compromised spender can deliberately burn the entire remaining budget; this feature does not prevent that loss.

## Representation

`GasData.owner` names a mutable shared `sui::gas_allowance::GasAllowance` input, `GasData.payment` is empty, and the gas price is positive. The shared object contains an immutable funder, an immutable spender, a `Balance<SUI>` escrow and a permanent revocation bit. The funder creates and funds it in a signed transaction. Funder-only operations add funds, withdraw a specified amount, or revoke and return the remaining balance. The revoked shared object remains as a tombstone; revocation cannot be undone.

The native framework already has `sui::allowance::Allowance<T>`, but that type intentionally returns unrestricted balances through its public spend APIs. Its policy executes in Move and rolls back on failure. Gas charging must also work after a Move abort or OOG failure. Reusing that type would not enforce gas-only spending.

Address-balance escrow was considered. The existing empty-payment gas path uses the address-funds scheduler, while a UID-gated funder withdrawal uses object-funds accounting. Sharing an accumulator address between these reservation domains requires additional ordering/accounting work. Keeping the small escrow inside the mutable shared object uses existing shared-object version sequencing for both gas charges and funder operations. It introduces no separate allowance balance ledger or balance-scheduler exception.

## Authentication and extraction boundaries

The transaction shape selects allowance payment before signature verification; it does not authorize an arbitrary object. Signing validates the exact framework type, shared ownership, mutable declaration, designated spender, revocation state and full gas budget. The dedicated protocol gate rejects this mode before activation. Ordinary sender/sponsor signatures are unchanged.

The allowance input cannot be referenced by PTB commands. Every use of `Argument::GasCoin` is rejected for allowance gas, irrespective of the versioned rule for ordinary address-balance gas. Native allowance payment exposes no runtime gas coin, no `Withdrawal`, and no `UID` to Move. Managing an allowance requires the funder's signature and a different gas payment source; the managed allowance cannot pay for a command that references itself. Explicit sponsor withdrawals and legacy coin-reservation ownership checks remain in force.

`TxContext::sponsor()` does not impersonate the funder or the allowance object for this mode: neither is a transaction signer. The sender remains the spender.

`GasPaymentMode` is the shared structural decoder for signing, execution and RPC. It does not replace protocol or loaded-object validation. `gas_payer_address()` returns `None` for allowance payment; payer indexes, GraphQL filters and CLI sponsor handling must not interpret the allowance ID as an address. The wire `gas_owner` field, including analytics that copy it, remains a payment selector rather than the funder's address.

RPC resolution infers the allowance's mutable access from native gas settlement, since PTB command-use inference cannot discover it. Automatic selection preserves allowance payment, validates the live escrow and estimates an omitted budget using at most the escrow balance. It does not search for coins or an address balance at the allowance ID.

The CLI delegates missing budgets and gas selection to this RPC path, but retains the locally constructed commands, inputs, sender, gas owner and gas price. Only an omitted budget, omitted ordinary gas coins and the resolved expiration are taken from the response. Allowance mutability is normalized locally. A fullnode response cannot replace the user's PTB before signing. Already serialized transaction data retains its payment selector and expiration, and signing follows `required_signers()` rather than treating a selector as a sponsor address.

New allowance dry-run and dev-inspect transactions use the same resolution path, including bounded validity, an omitted budget and allowance mutability. Complete serialized transactions still retain their supplied fields. Inspection does not commit the simulated allowance charge.

## Admission, execution and ordering

Signing requires escrow sufficient for the entire declared gas budget. Execution rechecks the consensus-sequenced authorization and remaining escrow. Concurrent spends, funder withdrawals and revocation conflict on the same mutable shared object. If a previously accepted transaction reaches an exhausted, revoked or unavailable allowance, it fails without running Move or charging another payer. It uses a deterministic zero-charge version-bump outcome.

When storage provenance is enabled, paid transactions must also have enough budget to prepay provenance reads for every exclusive mutable input. Input checking probes the active gas meter before execution or non-revertible gas smashing. An insufficient budget is rejected without execution or charge, rather than entering recovery with unpaid lookups. The successful path uses one probe; only rejection diagnostics search the meter for the exact required minimum. This input-dependent minimum applies to ordinary payers too. Gasless and system transactions retain their separate admission policies.

An admitted execution charges the existing computation/storage meter, including failed execution and OOG. Only the actual charge is removed from escrow; an unspent budget is never materialized as a spender balance. The balance cannot underflow because execution admits only a full-budget reserve and the gas meter bounds the charge. Native charging occurs after PTB failure/reset handling, so Move rollback cannot erase it.

Revocation takes effect in shared-object consensus order. It cannot undo charges ordered before it. A transaction with no owned inputs retains the existing bounded epoch-validity requirement and digest replay protection. The shared object adds a serialization and congestion cost; independent allowances can execute independently.

### Admission and cancellation economics

Signing is not a reservation across in-flight transactions. Multiple transactions can pass the same balance check before earlier spends or revocation make the escrow unavailable. These transactions still consume admission, consensus and versioning work. They do not run Move, cannot overdraw escrow and cannot charge a fallback payer.

This follows the existing stale address-balance `InsufficientFundsForWithdraw` policy: `address_balance_tests::test_insufficient_balance_charges_zero_gas` submits competing pre-admitted withdrawals and requires the losing transaction to charge zero. Owned gas coins also receive vote-time version validation without locks; conflicting owned references are locked only after consensus. Allowance transactions retain the existing replay-protection check, scheduler deduplication and overload checks. Without address-owned inputs or coin reservations, validity is limited to at most two epochs. These controls bound individual transactions and admission capacity; they do not collateralize every transaction admitted to consensus.

A native single-validator run reused one payer for 100 settled five-transaction soft bundles per payment mode, replenishing to 20,000,000 MIST between waves and declaring that budget on every spend. Both modes produced 100 successes and 400 zero-charge losers. Address-balance spending charged 100,000,000 MIST; allowance spending charged 100,019,400 MIST. Spending advanced the allowance 500 versions, including 400 zero-charge mutations; address-balance losers mutated no objects. Median settled latency excluding replenishment was 485ms and 601ms respectively; the full loops including replenishment took 107.1s and 108.1s. Funding transactions are excluded from spend counts. This repeated localhost workload demonstrates the extra allowance version/write work; it is not saturation, cold-disk, multi-validator or production-liveness evidence. Mainnet/testnet activation would need an explicit decision on that unpaid shared-object work.

Congestion and randomness cancellation retain a normally version-assigned allowance input while other cancelled shared inputs use their existing sentinels. The scheduler waits for that allowance version; it participates in Lamport computation and its shared-object cursor advances. A funded, authorized allowance pays cancellation gas without running Move. Nonserialized execution metadata carries only the allowance ID when it replaces a congestion sentinel. Checkpoint execution and replay reconstruct that one missing bit; the cancellation reason and all other congested IDs are decoded independently from the remaining input sentinels. Ordinary transactions never import an expected cancellation error. If the sequenced allowance is already exhausted or revoked, the zero-charge unavailable-payer rule still applies.

Consensus accounts for native allowance work using `gas_allowance_congestion_control_cost` (1,000 microseconds in protocol 142). Normal scheduling takes the maximum of that floor and the PTB execution estimate, so a zero-command allowance transaction cannot claim zero scheduling cost. Cancellation, including failed randomness, adds only the retained allowance's native settlement cost; unexecuted commands and sentinel inputs do not acquire debt. That cost carries into later commits. It is a scheduling policy value, not a measured latency bound or a gas charge. Cancellation can still exceed the ordinary per-commit burst budget; finite commit sizes and existing deferral limits remain relevant. This accounting does not reserve escrow or eliminate unpaid losing writes.

No allowance-specific pre-consensus reservation is introduced. The existing address-funds scheduler runs after consensus and cannot supply that guarantee either. A prepaid-consensus guarantee would require a separate admission protocol with durable or consensus-reconstructible reservations and reconciliation for actual charges, cancellation, expiry, restart, top-up, withdrawal and revocation. Reserving the funder's address balance would reserve the wrong funds. This implementation uses Sui's existing vote-only admission policy and guarantees atomic escrow solvency and gas-only use. Mainnet/testnet activation remains absent.

## Storage rebates and delayed extraction

Returning the current transaction's refund to the funder is insufficient. Existing Sui storage fees become an object's `storage_rebate`. Without attribution, the spender could create an object with allowance gas and later delete or shrink it with self-paid gas, collecting the original funder's storage payment. Transfer to an accomplice would have the same effect.

Native child metadata records `(UID, recipient, amount)`, where `amount` is the protected **raw** storage rebate, before rebate-rate rounding. A new object's allowance-funded deposit is protected. For an existing object with raw deposit `D` and protected amount `P`, the reusable, unprotected deposit is `U = D - P`. If its replacement deposit is `D'`, an allowance protects only `max(D' - U, 0)`. It does not claim storage that a previous ordinary payer already funded.

When a protected object is rewritten, wrapped or deleted, its protected portion and the marker's own deposit go to the recorded funder. The unprotected portion remains available to the current gas payer. Transfers do not transfer the protected refund entitlement. New allowance-funded storage records the new funder; ordinary replacement storage needs no marker. Immutable outputs cannot later yield a storage refund and need no marker.

The paying allowance may recycle protected parent and marker deposits whenever their recipient is its own funder, including deposits on ordinary objects and deposits funded through another allowance. It retains provenance for transactions paid by someone else. An unchanged-size rewrite therefore does not move the old deposit into the funder's address balance while requiring escrow to finance its replacement.

`StorageRebate` has no `store` ability and exposes no Move constructor or UID accessor, so outside code cannot publicly receive or transfer it. A marker's ID is derived from the parent ID, its native-only type and an empty name. Its `ObjectOwner(parent)` ownership prevents it from being supplied as an address-owned transaction input. It does not create a marker of its own. Markers remain visible as ordinary object records in effects and object APIs; `ListDynamicFields` returns only actual `Field<K, V>` objects.

Protected deposits owed to a different payer are excluded from usable rebates before budget checks. Settlement moves their raw value into one funder-owned `StorageRebate` claim per recipient and transaction. The deposit stays in the storage fund; it is neither credited to the spender nor returned to allowance escrow. Claims survive revocation. The funder signs an ordinary transaction calling `gas_allowance::claim_storage_rebate` to redeem them. Deleting a claim applies ordinary rebate rounding and gas charges at redemption, rather than charging the rebate fee twice.

The claim ID derives from its recipient, native type and transaction digest, disjoint from child-marker IDs. Its recorded protected amount is zero; its own `storage_rebate` holds the carried deposit. The entry function checks the recipient, and object-owned markers cannot be supplied as claim inputs. Effects retain their existing gas-cost interpretation: `net_gas_usage()` reports the current payer's net gas charge, not other funders' refunds. No settlement event, alternative payer summary, or event decoder is needed. An allowance's own negative-net surplus is credited to its funder rather than replenishing escrow; Rosetta reports that actual balance change without inventing an address payer for the allowance ID.

Unmetered system transactions use the same claim mechanism. Epoch execution cannot append deposits after the final accumulator settlement, so protected deposits remain in funder-owned claims. Only unprotected system rebates continue to pool into `0x5`.

Settlement prepares a provenance plan, meters replacement parent deposits, and applies marker changes through the temporary store's native object helpers. Failure/reset handling discards attempted writes and refund bookkeeping together. Retained protected inputs keep their original deposits and markers instead of making a failed ordinary payer finance replacement storage. This also applies to storage-OOG recovery. Storage conservation validates carried input and output deposits, requires equal carried totals, and accounts for the remaining metered portions separately. A partially protected deposit still returns its unprotected portion to the current payer. Claims for protected secondary gas coins survive gas smashing followed by a Move abort.

Metadata reads, including misses, use the protocol's `storage_rebate_lookup_bytes` charge (256 bytes in version 142). Declared mutable-input lookups are prepaid before Move execution so input-only OOG recovery can still inspect provenance. Runtime-child lookups are charged before reading them. System execution remains unmetered. This adds provenance lookup work and read gas to ordinary payers as well as allowance payers whenever storage provenance is enabled: an ordinary transaction can delete or mutate an allowance-funded object and must not collect its protected deposit. Restricting lookup to allowance-paid transactions would reintroduce delayed extraction. The unchanged object envelope has no provenance bit that could safely skip these misses. A stored child is created only when a mutable output has a protected deposit. Protocols where provenance has not activated take neither the lookup nor the additional charge.

The extra reads cross computation buckets for larger transactions; ordinary users therefore pay higher fees with this gate enabled. Enabled runs recorded 62, 852, 6590 and 26362 negative object-cache hits across the corresponding 25-simulation measurement windows, including background work. These warmed debug-build localhost measurements show lookup work scaling with input count; they are not physical disk-read counts, cold-cache benchmarks or production throughput results. The sequential off/on runs and noisy latency tails do not establish a latency bound. Mainnet/testnet activation would need explicit gas-pricing and cold-cache capacity assessment.

RPC estimation simulates explicitly selected gas coins with their real identities and provenance. For estimation only, it appends a synthetic secondary coin that replaces the reserved gas budget, capped by `u64` balance headroom. This keeps below-cap primary coins spendable during estimation. Estimation uses the protocol's maximum budget rather than the selected coins' balance, so an underfunded payment can receive a complete funding quote; an out-of-gas estimation is reported as execution failure instead of a truncated quote.

Automatic selection first estimates with its existing mock coin. If selected coins have protected deposits, it re-estimates once with those actual coins and the same synthetic funding. The RPC server uses the native marker-ID helper for this probe; ordinary unprotected automatic payment avoids the extra execution. Synthetic funding never enters the returned or signed transaction. Final simulation uses only the actual payment and resolved budget.

Insufficient-funding estimates expose `INSUFFICIENT_GAS_BALANCE` error metadata with `requiredBudget`. Automatic wallet selection retains `owner`, `coinBalance` and `addressBalance`; explicitly or automatically selected payment shortages report `selectedPaymentBalance`. Allowance shortages report `allowanceId` and `allowanceBalance`, never a fictitious wallet address or coin balance. Semantic execution failures take precedence over a partial funding quote.

## Protocol and serialization

Protocol version 142 enables `enable_gas_allowances` and `enable_storage_rebate_provenance` only on devnet/Unknown, with a 256-byte provenance lookup charge and a 1,000-microsecond native allowance scheduling floor. Versions through 141 and mainnet/testnet remain unactivated. Framework creation, signing and execution use the allowance-payment gate.

The flags have different lifecycles. A future protocol can disable allowance creation/payment while preserving funder management and claim redemption with ordinary gas. Storage provenance is irreversible once funded deposits exist: its processing, admission prepayment and lookup pricing must remain enabled even when allowance payments are disabled. Otherwise, the next ordinary payer could collect an existing funder's protected deposit. Disabling payment does not remove the ordinary-traffic provenance costs.

The payment envelope, objects, effects and checkpoints retain their existing BCS layouts. The new framework types use ordinary Move object contents for the escrow, protected refund metadata and claims. There is no new transaction or object-data enum variant and no two-PR decoder rollout is required by this representation. Mainnet/testnet activation is intentionally absent. SDKs constructing these transactions must identify the allowance input and use spender-only signing; older SDK sponsorship assumptions may require client updates even without a BCS change.

## Verification requirements

Coverage includes an unfunded spender, repeated spender-only authorization, wrong spender/type, exhaustion, full-budget admission, gas/allowance argument extraction, balance withdrawals, failed execution/OOG, funder withdrawal/revocation, concurrent budget contention, replay and epoch validity. Storage regressions cover funder claims after revocation, ordinary third-party mutation, mixed protected/unprotected inputs on abort, protected secondary gas-coin smashing, repeated large-object and nested-allowance deposit recycling, marker inaccessibility, and the staking/epoch-transition extraction sequence followed by redemption. RPC coverage includes omitted budgets, protected gas coins at low reference gas price, and marker filtering under full and ID-only field masks. Native CLI regressions exercise serialized allowance payment with funded and unfunded spenders and omitted budgets for protected-object rewrites. Rosetta covers successful and failed allowance spends and funder surplus refunds. A full Move-event-quota transaction verifies that claim creation preserves user events. Cancellation tests replay ordinary and allowance payments from effects and reject expected errors that disagree with available sentinels.

The protocol-transition regression disables allowance payment, then mutates previously funded storage with ordinary gas and redeems the funder's claim. Estimation regressions exercise below-cap explicit coins, complete funding quotes for underfunded payments, structured semantic failures rather than partial quotes, and protected refund claims after selected-coin payment.

Congestion regressions cover zero-command allowance work, repeated cancellation debt across commits, sentinel inputs, and the native cost floor's protocol gate. Consensus execution and effects replay must agree even when earlier certificate denial masks allowance congestion.
