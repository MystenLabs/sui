Compliance operations add gas cost and throughput considerations to regulated asset transactions on Sui. Understanding these costs is essential for designing efficient compliance flows, choosing batch strategies, and planning indexer capacity for production workloads.

This page covers the performance characteristics of each compliance primitive. For background on gas mechanics, see [Gas in Sui](/develop/transaction-payment/gas-in-sui).

## Gas cost by operation type

### Deny list enforcement

The [deny list](/onchain-finance/compliance/deny-list-operations) is enforced at the protocol level during transaction validation. When a transaction involves a regulated currency, the validator checks the sender and recipient against the `DenyList` shared object.

This check is part of the standard transaction validation path. It does not add a separate Move execution cost. The cost is absorbed into the base transaction processing overhead.

Adding or removing addresses from the deny list through `deny_list_v2_add` or `deny_list_v2_remove` calls are Move transactions that access the shared `DenyList` object (`0x403`). Each call has a gas cost that includes:

- Shared object access for `DenyList`.
- Dynamic field read and write for the specific currency type's deny entries.
- Storage cost for the new deny list entry (on add) or storage rebate (on remove).

### Policy rule evaluation

[Token policy rules](/onchain-finance/closed-loop-token/rules) execute as Move function calls during transaction processing. The gas cost of policy rule evaluation depends on:

- **Number of rules:** Each rule added to a [TokenPolicy](/onchain-finance/closed-loop-token/token-policy) runs its `verify` function during action request processing. Gas scales linearly with the number of rules.
- **Rule complexity:** A rule that reads a dynamic field on a shared object costs more than a rule that checks a field on an owned object. Rules that access the `Clock` object or perform multiple lookups cost proportionally more.
- **Shared object contention:** If a rule accesses a shared object (such as an attestation registry), transactions touching that object are sequenced by the [consensus](/develop/sui-architecture/consensus) protocol. This does not increase gas cost per transaction, but it limits the transaction throughput for operations involving that shared object. Learn more about [shared objects](/develop/objects/object-ownership/shared).

To minimize policy rule gas costs:

- Keep rule `verify` functions focused. Perform only the checks necessary for that rule.
- Prefer owned object inputs (such as user-held attestation objects) over shared object lookups when the compliance model allows it.
- Avoid redundant checks across rules. If two rules both need to read the same data, consider merging them.

### Event emission

Emitting [compliance events](/onchain-finance/compliance/compliance-events) during transaction execution adds gas cost proportional to the size of the event data. Each `sui::event::emit` call has a cost based on:

- The size of the event struct in bytes.
- The number of events emitted per transaction.

Event emission costs are generally small relative to other transaction costs. However, for transactions that emit many events (for example, a batch deny list update that emits an event per address), the cumulative cost is meaningful.

Design event schemas to include only the data needed for compliance reporting. Avoid including large dynamic fields or redundant data in event structs.

## Batch operation strategies

Batching multiple compliance operations into a single [programmable transaction block](/develop/transactions/ptbs/prog-txn-blocks) reduces the per-operation overhead by sharing the base transaction cost across all operations.

### Deny list batch updates

When processing a sanctions list update with many addresses:

- Combine all `deny_list_v2_add` calls into a single PTB.
- Each call adds its own computation and storage cost, but the base transaction overhead (signature verification, shared object locking for `DenyList`) is paid once.
- The `DenyList` is a shared object, so the entire batch is sequenced as a single transaction rather than competing with other deny list updates.

:::info

There is a maximum transaction size and gas budget limit on Sui. For very large batch updates (hundreds of addresses), split the updates into multiple transactions of a manageable size. Test on [Testnet](/develop/sui-architecture/networks) to determine the practical batch size for your gas budget.

:::

### Batch attestation operations

If issuing or revoking multiple [attestation objects](/onchain-finance/compliance/identity-gating) at once:

- Combine the creation or revocation calls into a single PTB.
- If attestations are stored as dynamic fields on a shared registry, all operations in the batch touch the same shared object. This is sequenced as a single transaction.
- If attestations are individual owned objects, each creation is an independent command within the PTB and can benefit from Sui's parallel execution for non-conflicting objects.

## Indexer throughput planning

Compliance event indexing must keep pace with the event generation rate. For high-volume regulated assets, plan your [indexing pipeline](/develop/accessing-data/custom-indexer/custom-indexers) capacity based on:

### Event volume estimation

Estimate the peak event volume by multiplying:

- **Transactions per second (TPS):** The expected peak transaction rate for your regulated currency.
- **Events per transaction:** The number of compliance events emitted per transaction (typically 1 to 3 for a standard transfer with policy evaluation).
- **Event size:** The average size of each event struct in bytes.

For example, a regulated stablecoin processing 100 transfers per second with 2 compliance events per transfer generates 200 events per second. At an average event size of 200 bytes, this produces approximately 40 KB/s of raw event data.

### Indexer capacity requirements

Your compliance indexer must handle:

- **Ingestion rate:** Processing events at the peak rate without falling behind. The [indexer framework](/develop/accessing-data/custom-indexer/pipeline-architecture) processes checkpoints sequentially, so the indexer must process each checkpoint's events before the next checkpoint arrives.
- **Enrichment overhead:** Joining onchain events with offchain identity data adds latency. If the KYC provider lookup is slow, this becomes the bottleneck.
- **Storage growth:** Compliance events accumulate over time. Plan storage capacity based on daily event volume multiplied by the regulatory retention period.
- **Query performance:** Compliance reports often scan large time ranges. Index your compliance database for the query patterns described in [Compliance Events](/onchain-finance/compliance/compliance-events).

### Monitoring

Monitor your compliance indexer for:

- **Lag:** The difference between the latest onchain checkpoint and the latest processed checkpoint. Alert if lag exceeds your compliance SLA.
- **Error rate:** Failed event processing or enrichment attempts. These represent compliance events that are not being recorded.
- **Storage utilization:** Approaching storage limits that could cause the indexer to stop.

## Cost optimization summary

| Strategy | Impact | Tradeoff |
| --- | --- | --- |
| Batch deny list updates into PTBs | Reduces per-address base transaction cost | Larger transactions have higher total gas; shared object sequencing limits concurrency |
| Use owned attestation objects instead of shared registry | Avoids shared object contention; enables parallel execution | Issuer loses direct control over attestation lifecycle |
| Minimize policy rule count | Reduces per-transfer gas cost | Fewer rules might mean less granular compliance checks |
| Use compact event schemas | Reduces event emission gas cost | Less data per event might require additional offchain lookups |
| [Sponsor transactions](/develop/transaction-payment/sponsor-txn) for compliance operations | Users do not need to hold SUI for gas | Sponsor bears the gas cost; requires gas station infrastructure |
