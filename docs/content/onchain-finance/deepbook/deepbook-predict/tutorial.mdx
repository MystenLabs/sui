A complete DeepBook Predict flow on Sui Testnet covers pricing a market board, creating an account, quoting and minting directional and two-sided range positions, closing before and after settlement, and running the queued liquidity provider flow. It continues from the [DeepBook Predict quickstart](/onchain-finance/deepbook/deepbook-predict), which covers install, funding, and a first mint.

Every transaction and every read on this page goes through the `/predict` subpath of `@mysten/deepbook-v3`. The SDK builds transactions and never signs them, and every read it exposes runs against the Sui client core API, so no indexer or server sits on the critical path. The samples live in the `examples/deepbook-predict` package, which type-checks with `npm run build` (`tsc --noEmit`). This document does not execute them against Testnet, so run the [manual verification steps](#verify-on-testnet) before you rely on the write paths.

:::caution

DeepBook Predict runs on Sui Testnet only. There is no Mainnet deployment. Package IDs, object layouts, and function signatures on these pages are pinned to the `predict-testnet-8-21` branch of the deepbookv3 repository, and they can change before any Mainnet release.

:::

## Configuration and client

Keep every Testnet-only identifier in one configuration block, and assert the deployment name at startup. A later SDK release can intentionally move Testnet to a newer deployment, so an unchecked upgrade silently repoints your application.

`getDeployment('testnet')` returns the deployment name `predict-testnet-8-21`, the chain ID `4c78adac`, and the source commit the SDK generated its configuration from. `getUnits('testnet')` returns the unit constants for that deployment: a fixed-point scale of `1000000000` for probabilities, prices, and rates, 6 decimals for both the DUSDC quote coin and position quantities, and a position lot size of `10000` raw units, which is $0.01 of payout.

Register the Predict extension on any client that exposes the core API. The following example uses the [gRPC](/develop/accessing-data/grpc) client.

<ImportContent source="examples/deepbook-predict/src/client.ts" mode="code" tag="client" />

`predict({ network: 'testnet' })` lands the extension on `client.predict`, which exposes three groups. `tx` builds ready-to-sign transactions, `read` runs simulations and object reads, and `decode` parses receipts out of an executed transaction's events with no network call at all. Passing `'mainnet'` throws at construction, because no Mainnet deployment exists.

### Errors the SDK raises

Two typed errors cover almost every failure you handle in application code:

- `PredictInputError`: Client-side validation rejected the call before it built anything. Common causes are an unknown underlying, a strike off the tick or admission grid, a quantity that is not a whole lot, an amount carrying more decimals than the coin allows, and a range whose `lower` is not below `upper`.
- `PredictMoveError`: A simulation hit a Move abort. It carries `module`, the exact `code`, and `abortName`, the `E`-prefixed constant name. `abortName` is `null` over JSON-RPC, because only gRPC and GraphQL surface the clever-error constant name.

Both quote methods dry-run the real transaction, so they raise the same errors the write would. Treat a successful quote as a preflight.

## Understand the oracle

Predict owns no oracle. Pricing inputs live in the separate `propbook` package as three shared objects per underlying: a `PythFeed` holding exact-timestamp spot observations, a `BlockScholesValueStore` holding spot and forward observations, and a `BlockScholesSVIStore` holding the SVI volatility surface. One underlying is live on Testnet, BTC, with propbook underlying ID `1`.

Every priced call rebuilds a transaction-local `Pricer` from those objects through `expiry_market::load_live_pricer`. `Pricer` has `copy` and `drop` but not `store`, so it never persists between transactions, and it binds to exactly one `ExpiryMarket`. The SDK resolves the oracle objects from the deployment configuration, so you never pass an oracle object ID yourself.

Freshness bounds are protocol configuration, and pricing aborts on a stale input. This deployment's initial configuration requires the Pyth spot and the Block Scholes spot and forward within 10 seconds, and the Block Scholes SVI surface within 60 seconds. Read the live values from the `ProtocolConfig` shared object rather than assuming them, because the deployment manifest records only an initial snapshot.

### Discover markets

`read.markets()` returns every active market. Each entry describes one `ExpiryMarket` shared object:

| **Field** | **Meaning** |
|-------|-------------|
| `id` | The `ExpiryMarket` shared object ID |
| `expiryMs` | Expiry as a Unix millisecond timestamp, typed `bigint` |
| `tickSize` | Strike grid granularity in USD |
| `admissionTickSize` | The coarser grid a numeric strike must land on |
| `mintPaused` | Whether minting is paused for this market |
| `referencePrice` | The window's anchor strike in USD, or `null` until the keeper seeds it |

<ImportContent source="examples/deepbook-predict/src/markets.ts" mode="code" tag="markets" />

`read.market({ underlying, expiryMs })` returns the same fields plus `nav`, the market's current net asset value, and returns `null` when no market exists at that expiry.

Testnet runs 5 enabled cadences for BTC: 1m, 5m, 1h, 1d, and 1w. A 1mo cadence is configured but disabled. A new 1m market is created every minute. `tickSize` is $0.01 on every enabled cadence, while `admissionTickSize` is $1 on the 1m, 5m, and 1h cadences and $100 on the 1d and 1w cadences.

### Ticks, strikes, and position shape

A position is a half-open range on an absolute integer tick grid, `(lower_tick, higher_tick]`. Direction is a special case of that range rather than a separate concept: a down position is `(0, K]` and an up position is `(K, 1073741823]`, where `0` is the negative-infinity sentinel tick and `1073741823` is the positive-infinity sentinel. The fully open range is rejected.

The SDK hides the tick arithmetic behind a market descriptor with two arms:

- **Directional:** `{ underlying, expiryMs, side: 'up' | 'down', strike }`, where `strike` is a USD number or the literal `'reference'`.
- **Two-sided range:** `{ underlying, expiryMs, side: 'range', lower, upper }`, where both bounds are finite USD numbers and `lower` sits below `upper`.

An optional `marketId` on either arm pins the exact `ExpiryMarket` and skips the registry lookup. The SDK validates the ID and rejects a pin whose expiry disagrees with the descriptor.

A numeric strike must land on the market's `admissionTickSize` grid, not just the finer `tickSize` grid. The market's `referencePrice` is the one finite off-grid boundary the chain admits, and `strike: 'reference'` selects it. That literal works on the directional arm only, and it throws when the keeper has not seeded the reference price yet.

### Price a whole board from one chain read

`read.price({ underlying, expiryMs, strike })` returns `{ up, down }` as probabilities between 0 and 1 for a single strike. It takes no `side` and always returns both.

`read.pricer({ underlying, expiryMs })` loads the pricer once and hands back a local calculator, so a board of dozens of strikes costs one chain read:

| **Call** | **Returns** |
|------|---------|
| `pricer.up(strike)` | Probability that settlement lands above `strike` |
| `pricer.down(strike)` | Probability that settlement lands at or below `strike` |
| `pricer.range(lower, higher)` | Probability mass in `(lower, higher]`, floored at 0 |
| `pricer.strikeAtProbability(p)` | The strike whose up probability is `p`, or `null` when no crossing exists within 64 percent of the forward |
| `pricer.forward` | The forward price the surface anchors on |
| `pricer.asOf` | Source timestamps for the Pyth spot and the Block Scholes spot, forward, and SVI observations |

Every value here is a decimal float rather than chain fixed-point, and every calculation runs locally. Pass a `lower` of 0 or below for negative infinity and `Infinity` for an open upper bound. Check `asOf` before you render a board, because a pricer built from an observation that later goes stale still prices locally without complaint.

## Set up the account

Each owner has exactly one Predict account: a shared `AccountWrapper` object holding an `Account`. The wrapper holds your DUSDC balance, your PLP balance, and Predict's per-account data. A position is a packed order ID recorded against that account rather than an object in your wallet, so scanning owned objects never finds one.

`client.predict.tx.createManager()` takes no arguments and returns a transaction that creates the wrapper and shares it. The method name carries legacy DeepBook balance-manager naming; the object it creates is an account wrapper.

<ImportContent source="examples/deepbook-predict/src/create-manager.ts" mode="code" tag="create-manager" />

The wrapper address derives from the account registry root, so you do not need a transaction result to know it. `client.predict.wrapperIdFor(owner)` computes it offchain with no chain read, and that ID is what the account server paths key on. After execution, `decode.createManager(result)` reads the same `wrapperId` out of the events alongside `accountId`, `owner`, and `selfOwned`.

Creating a second account for the same owner aborts. To create and fund in a single transaction, `tx.deposit(owner, amountUsdc, { create: true })` composes the creation, the deposit, and the share. That form runs no pre-check, so it aborts when the account already exists, and `owner` must be the signing address because the registry derives the wrapper from the transaction sender.

Three calls cover funding and reading the account:

- **Deposit:** `tx.deposit(owner, amountUsdc)` sources DUSDC from your coin objects and your address balance.
- **Withdraw:** `tx.withdraw(owner, amountUsdc)` sends DUSDC to the owner's address balance. Pass `{ toCoinObject: true }` to receive a coin object instead.
- **Read the balance:** `read.balance(owner)` returns the account's DUSDC balance as a decimal number.

### Read account and position state

Account API paths key on the shared account wrapper object ID, not on the wallet owner address. `client.predict.wrapperIdFor(owner)` derives it.

```bash
$ ACCOUNT_WRAPPER_ID=0x...
$ curl "https://account-server-v4.testnet.mystenlabs.com/accounts/${ACCOUNT_WRAPPER_ID}/portfolio"
$ curl "https://account-server-v4.testnet.mystenlabs.com/accounts/${ACCOUNT_WRAPPER_ID}/balances"
$ curl "https://predict-server-v4.testnet.mystenlabs.com/accounts/${ACCOUNT_WRAPPER_ID}/positions?status=open&limit=100"
```

An open position whose market state includes a settlement is claimable. Claimability comes from the position and the market together rather than from a separate position status.

Four conventions apply across all three services:

- **Numbers arrive as strings:** Postgres `NUMERIC` values serialize as JSON strings. Parse monetary, quantity, probability, price, rate, and large identifier fields with decimal or bigint tooling rather than `parseFloat`.
- **Timestamps are milliseconds:** Onchain and event timestamps use Unix milliseconds unless an endpoint documents seconds. Raw event pages window on `from_ms`, inclusive, and `to_ms`, exclusive, while named history endpoints use `start_time` and `end_time` in Unix seconds.
- **Order IDs are market-scoped:** Packed order IDs are decimal `u256` strings and are unique only inside one expiry market, so identify a position by `expiry_market_id` and `order_id` together.
- **Raw events page oldest-first:** `GET /events` lists the allowlisted event resources and their filter profiles. Page one resource with `GET /events/RESOURCE`, then follow the opaque `page.next_cursor` with every filter unchanged until `page.has_next_page` is false. Unknown identifiers return `null` components or empty arrays rather than a 404.

## Deposit and mint a directional position

A directional position pays $1 per contract when settlement lands inside its range, and nothing otherwise. `quantity` is therefore the maximum payout in USD, and it must be a whole $0.01 lot.

Quote before you mint. `read.quoteMint(owner, descriptor, { quantity })` dry-runs the identical transaction `tx.mint` builds, so it doubles as a price preview and a preflight, and its fee numbers are exact rather than estimated:

| **Field** | **Meaning** |
|-------|---------|
| `entryProbability` | Fill probability between 0 and 1, per $1 of payout |
| `premium` | The premium alone, with no fees |
| `fees` | Exact `trading`, `subsidy`, `builder`, `penalty`, `referral`, and `inventoryImpact` components |
| `cost` | The all-in account debit, which is what `maxCost` caps |
| `quantity` | The payout the quote priced |
| `raw` | The same values as exact `bigint` chain amounts |

`fees.referral` is a portion of the trading fee rather than an extra debit, so `cost` excludes it. Pass `cost`, never `premium`, when you set a cap.

<ImportContent source="examples/deepbook-predict/src/mint.ts" mode="code" tag="mint-binary" />

:::caution

Mint slippage caps default to uncapped. Omitting `maxCost` and `maxProbability` sends `U64_MAX` for both, and the mint can then debit up to the full account balance at any fill probability the market admits. Always quote first and pass `maxCost`. Round it to at most 6 decimals, because a value carrying more decimals than the quote coin throws `PredictInputError` before the transaction is built.

:::

`decode.mint(result)` returns the receipt. Persist `orderId`. It is the only handle for closing or claiming the position, and nothing onchain enumerates an account's orders for you. The receipt also carries `lowerTick`, `higherTick`, `entryProbability`, `quantity`, `premium`, the exact fee breakdown, and a `raw` block of the same values as `bigint`.

To size by budget instead of by payout, `tx.mintAmount` takes `spend` as a premium budget, `minQuantity` as a payout floor, and the same `maxCost` ceiling. It rejects a `maxCost` of 0 or below before it builds anything.

## Mint a two-sided range position

A two-sided range pays out when settlement lands in the half-open band `(lower, upper]`, left-open and right-closed. It uses the same builder, quote, and close path as a directional position, with the range arm of the descriptor.

<ImportContent source="examples/deepbook-predict/src/mint-range.ts" mode="code" tag="mint-range" />

Both bounds are finite USD numbers that must land on the market's admission grid, and `lower` must sit below `upper`. `strike: 'reference'` has no meaning here, because the range arm carries no `strike` field. `read.quoteMint` accepts a range descriptor unchanged, and `pricer.range(lower, upper)` prices the band locally before you commit to it.

## Redeem and settlement

Closing a position takes one of two paths, and which one applies depends on whether the market has settled. The following sample quotes and closes a live position, then claims a settled one.

<ImportContent source="examples/deepbook-predict/src/redeem.ts" mode="code" tag="redeem" />

### Close a live position

`read.quoteRedeem(owner, descriptor, { orderId, quantity })` returns the net `proceeds`, the `gross` amount, an exact fee breakdown covering `trading`, `builder`, `penalty`, and `inventoryImpactRebate`, plus `quantityClosed` and `remaining`. `tx.redeem` builds the matching transaction.

A partial close retires the order and issues a replacement. Read `replacementOrderId` from `decode.redeem(result)` and update your stored ID, otherwise your next close targets an order that no longer exists. A live close also fails when it lands in the same millisecond timestamp as the mint.

:::caution

`tx.redeem` sends `minProbability: 0` and `minProceeds: 0` unconditionally, and the SDK exposes no option to raise either floor. A live close therefore accepts whatever the pricer returns at execution time. Quote immediately before you send, and treat the quoted proceeds as an estimate rather than a guarantee.

:::

### Settlement

Settlement is permissionless. Any address can call `expiry_market::try_settle`, which returns `true` when the market is now settled or was already settled, and `false` when it could not record a settlement. The call is idempotent, and it returns `false` before expiry.

Settlement needs an exact price at the market's expiry timestamp, and it looks for one in a fixed order:

1. **Exact Pyth spot first.** `try_settle` looks for a Pyth observation at exactly the expiry timestamp.
1. **Exact Block Scholes spot after a grace period.** When Pyth has nothing at that timestamp, the call waits 30 seconds past expiry, then tries the exact Block Scholes minute-boundary spot.

A market with neither exact observation stays unsettled, and later calls keep retrying. No approximation substitutes for the exact price, because an expired unsettled market has no solvency-safe mark.

Settlement emits `MarketSettled` carrying the `settlement_price` and a `settlement_source` of `0` for Pyth or `1` for Block Scholes. Trigger on that event rather than on the expiry timestamp, because the gap between expiry and settlement has no fixed duration.

### Claim a settled position

`tx.claimSettled(owner, { underlying, expiryMs }, { orderId })` closes a settled position. It takes no quantity, because the deployed `redeem_settled` closes the order in full. `decode.claim(result)` returns the `payout` alongside the market, account, and order identifiers.

### Permissionless redemption

`expiry_market::redeem_settled_permissionless` closes a settled position on the owner's behalf. Three properties define it:

- **Any address can call it:** The function takes no account `Auth`. It mints Predict's app authorization from the shared `AccountRegistry` instead, so the caller needs no capability, no relationship to the owner, and no signature from them. An admin can switch the path off by deauthorizing the Predict app on that registry.
- **It becomes available at settlement, not at expiry:** The market must be settled. Calling on an unsettled market aborts with `EMarketNotSettled`, and expiry alone does not settle a market. Call `try_settle` first, or wait for `MarketSettled`.
- **The payout goes to the owner:** The proceeds land in the owner's account, and only the owner can withdraw them. The caller pays gas and receives nothing.

The SDK does not build this call. `tx.claimSettled` builds the owner-authorized `redeem_settled` instead. Build the permissionless variant yourself as a `moveCall` against the Predict package, passing the `ExpiryMarket`, the `AccountRegistry`, the owner's `AccountWrapper`, the `ProtocolConfig`, the order ID, the accumulator root, and the clock. The `predict`, `account`, and `propbook` packages declare no `entry fun` at all, so every integrator call is a `public fun` invoked from a [programmable transaction block](/develop/transactions/ptbs/prog-txn-blocks), and several of them return values you must consume in the same block.

To find positions worth closing, `read.positions(owner)` walks the account's dynamic fields and returns `marketId` and `orderId` pairs, and `GET /accounts/ACCOUNT_WRAPPER_ID/positions?status=open` returns the same set from the index. Make any automated redeemer idempotent: the event stream delivers at least once, and another caller can close the same position between your check and your submission.

The protocol pays the caller no fee, rebate, or share of the payout, so no economic incentive exists for an unrelated party to run this. Treat it as infrastructure you run for your own users, or that an owner runs for themselves, and budget the gas as your own operating cost.

## Liquidity provider flow

Liquidity providers supply DUSDC to the shared `PoolVault` and hold PLP, a proportional claim on pool value. The pool is the counterparty to every Predict trade, so PLP value tracks pool profit and loss rather than a fixed yield.

Supply and withdrawal are asynchronous. Neither call mints or burns PLP. Each one escrows your funds, returns a queue index, and waits for the next pool flush, which prices both queues against one pool-wide mark.

:::info

You cannot trigger a flush. Only a holder of a market lifecycle capability starts one, through `start_pool_valuation`, followed by one `value_expiry` per active market and a single `finish_flush`, all inside one transaction. That single frozen mark is what stops anyone from timing an entry or exit against a self-supplied oracle update. Plan on filling at a price you do not control and cannot preview.

:::

### Supply liquidity

`tx.supplyPlp(owner, amountUsdc)` queues a supply request and escrows the DUSDC. The minimum request is 10 DUSDC.

<ImportContent source="examples/deepbook-predict/src/supply.ts" mode="code" tag="supply" />

`decode.plpRequest(result)` returns the receipt. Persist `index`. It is the handle for `tx.cancelSupplyPlp(owner, index)`, which reclaims the escrow any time before a flush processes the request. The receipt's `kind` is `'supply'` or `'withdraw'`, and `amount` is in quote units for a supply.

The SDK pins `minPlpOut` to `0`, so a supply carries no minimum share output. A queued request the flush cannot execute at the frozen mark, because the PLP price falls outside the executable band or the output rounds to zero shares, is cancelled and refunded rather than left queued or aborting the flush.

### Withdraw liquidity

`tx.withdrawPlp(owner, shares)` takes raw PLP shares as a `bigint`, not a USD amount. Read the balance with `read.plpBalance(owner)`, which returns the same raw `bigint`, and pass it straight through.

<ImportContent source="examples/deepbook-predict/src/withdraw.ts" mode="code" tag="withdraw" />

Cancel a queued withdrawal with `tx.cancelWithdrawPlp(owner, index)`, using the index from `decode.plpRequest`. The minimum withdrawal request is 1 PLP, and the SDK pins `minDusdcOut` to `0`. This deployment's initial configuration charges a 0.2 percent withdrawal fee and no supply fee. Read the live rates from the `ProtocolConfig` shared object, because the manifest records only the initial snapshot.

### Read vault state

`read.pool()` returns the pool aggregates:

| **Field** | **Meaning** |
|-------|---------|
| `plpTotalSupply` | Total PLP in issue, as a raw `bigint` |
| `idleUsdc` | The pool's idle DUSDC balance as a decimal number, excluding cash funded into expiries |
| `supplyRequestsPending` | The number of queued supply requests, not an amount |
| `withdrawRequestsPending` | The number of queued withdrawal requests, not an amount |

There is no synchronous share price. The pool prices PLP only inside a flush, at the mark that flush freezes, so no read returns a price you could trade against. Use `idleUsdc` and the queue depths instead to judge how much of a withdrawal the pool can settle soon and how many requests sit ahead of yours.

## Vault strategy considerations

These points follow from the protocol's documented mechanics. They are not investment advice.

- **You fill at the flush mark, not your own:** Both queues price against one pool-wide net asset value computed during the flush. That value moves between the moment you queue and the moment you fill, and no read previews it.
- **Exits are bounded by idle cash:** The flush fills supplies before withdrawals, so DUSDC supplied in a flush can pay that same flush's withdrawals. Cash already funded into an expiry is not directly redeemable until a rebalance or settlement returns it, so a large exit can fill across several flushes.
- **PLP value moves with open positions:** Each active expiry contributes its current net asset value to the pool, priced from live oracles, so your share value moves with trader positions and oracle prices even when you place no trade.
- **Backing is enforced per expiry:** Every expiry holds cash at least equal to its payout liability, and a per-expiry allocation cap snapshotted from cadence configuration bounds how much pool capital one expiry can put at risk.
- **A queued request can come back refunded:** A request the flush cannot execute at the frozen mark is cancelled and refunded rather than held, so handle a refund as a normal outcome rather than an error.

For the accounting model behind these limits, see [Design](/onchain-finance/deepbook/deepbook-predict/design).

## Verify on Testnet {#verify-on-testnet}

The write paths above type-check but this document does not execute them. To confirm the flow end to end:

1. Fund a Testnet address with SUI, then confirm the balance with `sui client gas`.
1. Request DUSDC, then confirm the balance with `sui client balance`.
1. Confirm all three services report an `OK` status on `/status`.
1. Call `read.markets()`. Confirm at least one market returns with `mintPaused` false and a non-null `referencePrice`.
1. Create the account, then confirm `client.predict.wrapperIdFor(owner)` resolves with `sui client object WRAPPER_ID`.
1. Deposit DUSDC, then confirm `read.balance(owner)` reports the deposit.
1. Call `read.quoteMint`, then mint with `maxCost` derived from the quote's `cost`. Confirm an `OrderMinted` event and record the `orderId`.
1. Mint a range position on two admission-grid bounds. Confirm a second `OrderMinted` event whose `lowerTick` and `higherTick` are both finite.
1. Quote and close part of the directional position. Confirm a `LiveOrderRedeemed` event and record `replacementOrderId`.
1. After an expiry passes, call `expiry_market::try_settle` and confirm a `MarketSettled` event. Claim with `tx.claimSettled` and confirm a `SettledOrderRedeemed` event.
1. Queue a supply of at least 10 DUSDC. Confirm a `SupplyRequested` event, then cancel it with the returned index and confirm a `RequestCancelled` event.
