A gas station is a backend service that pays gas on behalf of users or agents.

The recommended approach is [`@mysten-incubation/sponsor`](https://www.npmjs.com/package/@mysten-incubation/sponsor), which manages gas coin selection, splitting, and the dual-signature flow automatically. You supply a signer keypair and a validation policy; the SDK handles the rest. Sponsors pay from address balance using `setGasPayment([])`, which avoids locking specific coin objects and enables parallel transaction execution.

For custom requirements (self-managed coin pools, non-standard validation, multi-tenant isolation), see the [self-hosted gas station](#self-hosted-gas-station) section below.

## How it works

The sponsor handshake has six steps:

1. **Client builds a transaction without gas.** The client sets `sender` but omits gas payment, gas budget, and gas owner.

2. **Client sends the transaction bytes and signature.** The client sends already-built transaction bytes plus a user signature to the sponsor.

3. **Sponsor validates the transaction.** The service inspects the transaction, checks it against allowlists and budget caps, and rejects anything outside policy.

4. **Sponsor adds gas payment and signs.** The service sets `gasOwner`, `gasBudget`, and `gasPayment`, builds the final bytes, and signs them with the sponsor keypair.

5. **Sponsor executes.** The sponsor submits the dual-signed transaction to a full node.

6. **Sponsor returns the result.** The result is a discriminated union: `Rejected` (policy declined, no execution), `FailedTransaction` (executed onchain but aborted, gas still charged), or `Transaction` (success).

sequenceDiagram
    participant C as Client
    participant S as Sponsor SDK
    participant N as Full Node
    C->>C: 1. Build tx, sign
    C->>S: 2. Send bytes + signature

    S->>S: 4. Add gas, co-sign

### Built-in validators

| Validator | Rejects when |
|-----------|-------------|
| `validSender()` | sender unset or is gas owner |
| `onlyAddressBalanceGas()` | gas payment is not empty |
| `gasCoinNotUsed()` | a command uses the gas coin |
| `onlySenderWithdrawals()` | FundsWithdrawal is not the sender's |
| `userSignatureMatchesSender()` | user signature invalid or wrong signer |
| `gasBudget({ min?, max? })` | budget unset or out of range |
| `allowedPackages([...])` | MoveCall targets an unlisted package |
| `allowedFunctions([...])` | MoveCall targets an unlisted function |
| `simulationSucceeds()` | dry-run indicates failure |
| `boundedExpiration()` | expiration missing or beyond next epoch |

For full API details, see the [`@mysten-incubation/sponsor` documentation](https://sdk.mystenlabs.com/sponsor).

## Sponsoring agent transactions

When sponsoring transactions for an autonomous agent rather than an interactive user, the validation flow changes:

- **Identity verification:** The agent authenticates with an API key or presents a signed challenge instead of a wallet signature.
- **Spending mandate checks:** The gas station can verify that the agent has a valid [spending mandate](/onchain-finance/agentic-payments/spending-policies) onchain before sponsoring.
- **Per-agent budgets:** Track cumulative gas spend per agent address and enforce daily or weekly caps.

## Validation policies

Before sponsoring a transaction, validate it against a deny-by-default policy:

- **Command and package allowlist:** Sponsor only explicitly approved Move calls. Reject transfers, coin splitting or merging, publish, upgrade, intents, and every use of `GasCoin`; otherwise a client can transfer the sponsor's whole gas coin.
- **Inputs:** Bound command and input counts. Validate object IDs, recipients, and pure values required by every approved call. The example rejects all object inputs.
- **Type arguments:** Bound and allowlist them. An approved generic function still reaches arbitrary code through a caller-chosen type argument.
- **Budget and expiration:** The sponsor sets a fixed gas budget and short epoch expiration.
- **Simulation:** Dry-run the final transaction after attaching gas and reject unsuccessful execution before signing.
- **Identity and rate limits:** Authenticate callers and limit each credential and each sender independently.

## Monitoring and cost control

Track these metrics for your gas station:

- **Available gas coins.** Alert when the pool drops below 20% capacity.
- **Sponsorship volume.** Requests per minute, broken down by sender address.
- **Gas spend.** Total SUI spent on gas per hour. Compare against your budget.
- **Rejection rate.** Percentage of requests rejected by validation. A spike indicates possible abuse.

Set a maximum daily spend for the entire gas station. When the limit is reached, reject all new sponsorship requests until the next day or until an operator manually raises the limit.

### Gas coin pool

The sponsor address needs a pool of SUI coins to fund transactions. Two inflight transactions cannot use a single coin simultaneously. If you try, one transaction fails due to an object version conflict.

Because the pool is deliberately made up of many small coins, paginate when you load it: a single owned-objects page will not return all of them. Skip coins that cannot cover the gas budget, or the sponsor hands out a coin that only fails at simulation.

### Pool management

Track available gas coins in memory. When you use a coin for sponsorship, mark it as reserved until the transaction finalizes. The network always charges gas (even when a transaction fails), so the coin version changes in both cases. After finalization, re-fetch the coin to get its updated version before reusing it.

### Replenishment

Monitor pool size. When the number of available coins drops below a threshold, split more coins from a reserve. Automate this with a periodic check or trigger it when `acquire()` returns `null`.
