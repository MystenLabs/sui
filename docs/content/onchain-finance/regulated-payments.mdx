Regulated payment flows on Sui combine onchain enforcement primitives with offchain provider responsibilities. Sui provides the tools to enforce transfer restrictions, log events, and gate asset movement. Your payment provider or legal team handles identity verification, sanctions screening, fiat settlement, and regulatory reporting. This page explains where each responsibility sits and how to wire them together.

## Sui-owned compared to provider-owned

The following table shows which responsibilities belong to Sui primitives and which belong to your payment provider or legal team. Getting this boundary right is the foundation of a compliant payment architecture.

| Sui primitives (onchain) | Provider / legal team (offchain) |
|---|---|
| **DenyList** shared object at `0x403` with epoch-based enforcement | KYC identity verification (document checks, liveness, risk scoring) |
| **DenyCapV2** capability for per-address and global-pause controls | AML transaction monitoring and suspicious activity reporting |
| **PAS** Accounts, Policies, and approval witnesses for gated transfers | Sanctions list maintenance (OFAC SDN, EU, UN lists) |
| **Payment Kit** events (`PaymentReceipt`) for onchain audit trails | Fiat settlement and bank reconciliation |
| **Address balances** for stateless transfer construction | Chargeback resolution and refund processing |
| **TreasuryCap** governance for minting, burning, and supply control | Compliance reporting to regulators |
| **Sui events** for real-time streaming and historical queries | Legal opinions, licensing, and jurisdictional compliance |

:::info

Sui does not perform identity verification, screen transactions against sanctions lists, or settle fiat payments. These are provider-owned responsibilities. Sui provides the onchain enforcement layer that providers use to apply their compliance decisions.

:::

## Compliance architecture

A compliant payment system on Sui follows a four-layer model. Each layer builds on the one below it:

1. **Identity verification (offchain, provider-owned).** The payment provider verifies the user's identity through KYC checks, document verification, and risk scoring. This happens entirely outside Sui.

2. **Onchain attestation.** After verifying identity, the provider records an attestation onchain. The [Permissioned Asset Standard (PAS)](/onchain-finance/pas/pas-architecture) uses approval witnesses for this purpose. For example, a `KYCRegistry` contract can store verified addresses, and an approval witness checks the registry before stamping a transfer request.

3. **Token policy enforcement.** Transfer restrictions execute onchain through either [PAS Policies](/onchain-finance/pas/pas-workflows) (which require approval witnesses before allowing fund movement) or [DenyCapV2 deny lists](/onchain-finance/fungible-tokens/regulated-tokens) (which block specific addresses from sending or receiving regulated coins).

4. **Audit trail.** Every payment, approval, and deny-list change emits Sui events. Your compliance system subscribes to these events through [gRPC](/develop/accessing-data/grpc/using-grpc) or [GraphQL](/references/sui-graphql) to build an offchain audit log.

The key principle is that each layer is independent. You can use DenyCapV2 deny lists without PAS, or PAS without Payment Kit. Choose the combination that matches your regulatory requirements.

## KYC and AML boundaries

Sui does not perform identity verification. The network processes transactions from any address that holds the required assets and passes the onchain policy checks (deny list, PAS approval). Your provider must verify identity before allowing a user to interact with regulated assets.

### Where KYC fits

The [PAS integration guide](/onchain-finance/pas/integrating-pas) shows a `KYCRegistry` pattern where a provider-maintained contract stores verified addresses. The approval witness for a `SendFunds` request checks this registry before approving the transfer. If the address is not in the registry, the transaction fails.

This pattern separates concerns cleanly:

- The **provider** decides who passes KYC and updates the `KYCRegistry` onchain.
- The **PAS Policy** enforces that only registry-approved addresses can move funds.
- The **application** builds transactions that include the required approval calls.

### Where AML fits

AML transaction monitoring happens offchain. Your provider monitors transaction patterns, flags suspicious activity, and reports to regulators as required. When AML screening identifies a problematic address, the provider uses `DenyCapV2` to block it onchain (see [Admin operations](#admin-operations-freeze-revoke-and-global-pause) below).

## Admin operations: freeze, revoke, and global pause

The `DenyCapV2` capability lets you freeze individual addresses or pause all transfers of a regulated coin. This section provides an operational playbook for common admin actions.

### Freeze an address

To block an address from sending or receiving a regulated coin, add it to the deny list:

```bash
sui client call \
  --package 0x2 \
  --module coin \
  --function deny_list_v2_add \
  --type-args '0xPACKAGE::module::MY_COIN' \
  --args 0x403 $DENY_CAP_ID $ADDRESS_TO_FREEZE \
  --gas-budget 10000000
```

**Timing behavior:** The denied address cannot use the coin as a transaction input immediately. It can still receive the coin until the next epoch starts, at which point receiving is also blocked.

For the full Move and TypeScript code, see [Regulated Currencies](/onchain-finance/fungible-tokens/regulated-tokens).

### Unfreeze an address

Remove the address from the deny list:

```bash
sui client call \
  --package 0x2 \
  --module coin \
  --function deny_list_v2_remove \
  --type-args '0xPACKAGE::module::MY_COIN' \
  --args 0x403 $DENY_CAP_ID $ADDRESS_TO_UNFREEZE \
  --gas-budget 10000000
```

After removal, the address can use the coin as a transaction input immediately. Receiving remains blocked until the next epoch.

### Global pause

If your currency was created with `allow_global_pause: true`, you can freeze all transfers network-wide:

```bash
sui client call \
  --package 0x2 \
  --module coin \
  --function deny_list_v2_enable_global_pause \
  --type-args '0xPACKAGE::module::MY_COIN' \
  --args 0x403 $DENY_CAP_ID \
  --gas-budget 10000000
```

Use global pause for emergency situations only (security breach, regulatory order). Disable it with `deny_list_v2_disable_global_pause` when the situation resolves. Global pause blocks use as transaction inputs immediately, same as per-address deny. Receiving is blocked starting at the next epoch.

:::caution DenyCapV2 governance

The `DenyCapV2` holder can freeze any address or pause all transfers. Protect this capability with [multisig](/develop/transactions/transaction-auth/multisig) to prevent unauthorized freezes. See [Coin and capability security](/develop/security/best-practices#coin-and-capability-security) for governance best practices.

:::

## Sanctions screening with DenyCapV2

Sui does not maintain a sanctions list. Your compliance team or provider maintains the list (OFAC SDN, EU sanctions, UN lists) and uses `DenyCapV2` to enforce it onchain. The pattern is:

1. **Screen offchain.** Your provider checks user addresses against the sanctions list before onboarding and on a recurring schedule.
2. **Enforce onchain.** When screening identifies a sanctioned address, call `deny_list_v2_add` to block it. When an address is cleared, call `deny_list_v2_remove`.
3. **Monitor continuously.** Subscribe to deny-list change events to confirm that enforcement actions took effect.

This "watch-and-act" pattern keeps the sanctions list offchain (where it belongs, since lists change frequently and vary by jurisdiction) while using Sui's deny list for deterministic onchain enforcement.

### Batch screening

For bulk deny-list updates (for example, after importing a new sanctions list), submit multiple `deny_list_v2_add` calls in a single [programmable transaction block](/develop/transactions/ptbs/building-ptb). This reduces gas costs and ensures all updates apply atomically:

```typescript
import { Transaction } from '@mysten/sui/transactions';

const tx = new Transaction();

const addressesToFreeze = ['0xAddr1...', '0xAddr2...', '0xAddr3...'];

for (const addr of addressesToFreeze) {
  tx.moveCall({
    target: '0x2::coin::deny_list_v2_add',
    typeArguments: ['0xPACKAGE::module::MY_COIN'],
    arguments: [
      tx.object('0x403'),        // DenyList shared object
      tx.object(denyCapId),       // DenyCapV2
      tx.pure.address(addr),      // Address to freeze
    ],
  });
}

await client.signAndExecuteTransaction({ signer: adminKeypair, transaction: tx });
```

## Event-based compliance logging

Sui emits events for every payment, approval, and deny-list change. Build your compliance audit trail by subscribing to these events and storing them in your offchain logging system.

### Event sources

- **Payment Kit** emits events on every processed payment (both registry and ephemeral modes), including nonce, amount, coin type, and receiver. See [Payment Kit](/onchain-finance/payment-kit) for the event schema.
- **PAS** emits events for every request creation, approval, and resolution. See [PAS Workflows](/onchain-finance/pas/pas-workflows) for details.
- **Deny list changes** emit events when addresses are added or removed, or when global pause is toggled.

### Subscribing to events

Use gRPC subscriptions or the list APIs to capture compliance-relevant events in real time or historically. The `@mysten/sui` TypeScript SDK does not yet expose `SubscribeEvents` directly. Use the generated proto client or Buf CLI:

```shell
$ buf curl --protocol grpc \
  https://<FULL_NODE_URL>/sui.rpc.v2.SubscriptionService/SubscribeEvents \
  -d '{
    "filter": {
      "terms": [{
        "literals": [{
          "emitting_module": {
            "package": "0xYOUR_PACKAGE",
            "module": "my_coin"
          }
        }]
      }]
    }
  }' \
  --timeout 5m
```

For historical queries over a checkpoint range, use the [ledger history list APIs](/develop/accessing-data/grpc/using-grpc#ledger-history-list-apis). For event concepts and additional query patterns, see [Using Events](/develop/accessing-data/using-events).
