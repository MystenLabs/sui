Module staggered_submission 

Source
Expand description

Staggered consensus submission for transactions that do not restrict their proposers.

A transaction without a usable allowed-proposers list can be submitted to every validator at once, amplifying its consensus cost while paying gas once. Rejecting such transactions everywhere would break existing clients, so instead — when duplication is detected on the network — each validator derives a deterministic slot for itself from a stake-weighted permutation of the committee seeded by the transaction, and acts on its own submission according to that slot. The first paid_proposer_count validators in the derived order submit immediately (the proposer set an explicit list would be allowed), the validators up to the stake cut (STAGGER_PROPOSER_STAKE_BPS) wait long enough that an earlier copy can commit first, and every validator past the cut rejects the submission. Duplication is thereby bounded by construction instead of detected after its bandwidth is already spent.

Staggering applies on the consensus transaction pool path only: entries are held inside the pool and skipped by take() until eligible. A validator configured to use the push-based consensus adapter path instead submits immediately.

The slot is derived from the gas object ids rather than the transaction digest: digest derivation could be ground by re-signing trivial variants (nonce, budget) until each variant’s first slot lands on a different validator, while all such variants necessarily share their gas objects. Transactions paying from an address balance have no gas objects and fall back to the digest; the residual grindability there is accepted, since the variants still share the sender’s address balance and stay visible to sender-level accounting.

StaggeredSlot
A held submission’s registration against the stagger quota, carrying when the hold elapses. Armed while the entry occupies the caller’s queue: dropping it armed (the entry was discarded — insert failure, already-processed exclusion, eviction, flush) releases the registration automatically. release marks consumption into a proposal, and rearm re-registers on requeue after a dropped acknowledgement — bypassing the quota, just as requeues bypass pool capacity; any excess is transient.
StaggeredSubmission
Decides whether this validator should delay submitting a given user transaction to consensus, and by how much. It is inactive by default. The duplication signal in record_commit turns it on and off. A validator that restarts mid-epoch rebuilds its signal window from the commits after recovery, so its mode can lag its peers for a while. This is acceptable because staggering is a local policy.
