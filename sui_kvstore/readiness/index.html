Module readiness 

Source
Expand description

Decides when this instance has caught up after startup and can report ready.

For every pipeline, this instance compares its durable watermark (crate::DurableProgress) with two references, in chain time (timestamp_ms_hi_inclusive):

  • the pipeline’s stored watermark row, read once at startup: how far the instances running at that moment had got, and
  • the most advanced durable watermark any peer instance has streamed (crate::streamed_watermarks).

The instance is ready once every pipeline has recorded durable progress since startup and is at most max_lag_ms of chain time behind both references.

Recording durable progress proves this instance can ingest and write: each pipeline must commit at least once after startup. A pipeline records progress only when it commits new checkpoints, so while no new checkpoints arrive (for example during a chain halt), a restarted instance stays not ready. A rolling deployment then waits on it, and the instances it would replace keep serving.

The stored rows read at startup are fixed, so an instance that keeps making progress always catches up to them. Peers keep advancing: a restarted instance catches up faster than the chain advances and closes in on them, but an instance that stays more than max_lag_ms behind its peers (for example because its checkpoint source lags theirs) would never match them. Peers can therefore hold up readiness only for a bounded time after the instance has caught up to the stored rows: as long again as that took, and at least MIN_PEER_WAIT. While catching up to the stored rows, the chain moved on by the time that took; an instance that catches up at least twice as fast as the chain advances closes that gap within the same time again. Once the peer wait is over, the instance reports ready and logs the pipelines still behind its peers.

Peers that cannot be reached do not hold up readiness. Before reporting ready, the instance waits for every peer’s first response or for its first attempt to subscribe to fail, which is bounded by timeouts, so an instance that catches up to the stored rows quickly still compares itself with its peers.

Peers only hold back pipelines near their tip. A pipeline whose peer watermark is more than PEER_TIP_WINDOW of chain time behind the peers’ most advanced watermark across all pipelines is backfilling. Instances backfilling the same pipeline advance through chain time much faster than the chain does, so they rarely stay within max_lag_ms of each other; such a pipeline is compared only with its stored row read at startup.

Comparisons use chain time, not wall-clock time: if the whole system lags behind the chain tip, instances still become ready as soon as they match each other.

Readiness latches: wait_until_caught_up returns the first time every pipeline is caught up, and later lag does not make the instance unready again.

Constants§

MIN_PEER_WAIT
Minimum time peers can hold up readiness after the instance has caught up to the stored watermark rows read at startup.
PEER_TIP_WINDOW
How far, in chain time, a pipeline’s peer watermark can trail the peers’ most advanced watermark across all pipelines before the pipeline counts as backfilling and its peer watermark stops holding up readiness.
