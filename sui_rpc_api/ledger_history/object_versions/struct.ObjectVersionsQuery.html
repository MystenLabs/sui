Expand description

What a ListObjectVersions request lists: the object, the fields to render, the order, the limit, and the bounds the request sets. Public so other implementors of LedgerService parse requests, bound listings, end them, and mint cursors the same way.

Fields§

§object_id: ObjectID§read_mask: FieldMaskTree

The fields of each listed live version to render.

§removal_read_mask: FieldMaskTree

The fields of each listed removal to render.

§start_checkpoint: Option<u64>

start_checkpoint: list only the versions written in this checkpoint or later.

§end_checkpoint: Option<u64>

end_checkpoint: list only the versions written before this checkpoint.

§descending: bool

Whether to list versions from highest to lowest.

§limit: usize

The most items, live versions and removals, one stream lists.

pub fn has_held_after_cursor(&self, floor_checkpoint: Option<u64>) -> bool

Whether the request carries an after cursor whose client holds history right below the versions the listing lists that pruning through floor_checkpoint may have cut a gap after: an item’s cursor, whose item the client holds, or a boundary from a listing bounded by a checkpoint K below the floor, so that the lowest start_checkpoint the server accepts, the floor + 1, is above K + 1. This checkpoint rule is complete only for the boundary at version 0, below every version: its client holds what was written by the end of K, and pruning keeps every version written after the floor. A boundary above version 0 can sit at an end_version cut and vouches for nothing above it (see Self::needs_history_retained_from); the nothing-retained path and the low-start_checkpoint gate apply the checkpoint rule to it as ruled. With nothing pruned (floor_checkpoint unset), no boundary is held.

Whether the listing’s lowest version, start, is the one right after its after cursor, of either kind.

pub fn needs_history_retained_from( &self, start: SequenceNumber, floor_checkpoint: Option<u64>, ) -> bool

Whether a server whose listing floor is floor_checkpoint must find the object’s history retained from start, the listing’s lowest version, so as not to follow the history its client holds with a gap: the listing starts right after its after cursor (see Self::starts_after_cursor), which is an item’s cursor, a boundary that pruning through the floor passed (see Self::has_held_after_cursor), or a boundary above version 0. Such a boundary can sit at an end_version cut, below versions written by its checkpoint, so it vouches for nothing above it: the history from start is retained only when the object’s version at the floor is at most one above the boundary’s version, as it is for a boundary minted at the top of its window bounded at or above the floor. The boundary at version 0, below every version, keeps the checkpoint rule.

pub fn after_at_or_above(&self, version: Option<SequenceNumber>) -> bool

pub fn check_some_cursor_indexed( &self, window: &CheckpointWindow, upper_bound: &AtCheckpointUpperBound, ) -> Result<()>

Fails with OUT_OF_RANGE / ABOVE_LATEST_AVAILABLE (AtCheckpointUpperBound::check_cursor, naming the lowest of their checkpoints) when the listing runs to the tip (end_checkpoint unset, or above the checkpoint after the tip) and the request has cursors, all from listings bounded by a checkpoint above upper_bound’s highest indexed one: from servers that have indexed further than this one. A cursor from a listing bounded at or below it names a version this server has indexed.

pub fn floor_error( &self, floor_checkpoint: u64, upper_bound: &AtCheckpointUpperBound, ) -> RpcError

The error for a request a server whose listing floor is floor_checkpoint cannot serve because pruning took history it would list: OUT_OF_RANGE / BELOW_EARLIEST_AVAILABLE (below_serving_floor), reporting floor_checkpoint + 1, the lowest start_checkpoint it accepts, as lowestAvailableCheckpoint. A request whose after cursor comes from a listing bounded above upper_bound‘s highest indexed checkpoint, by a server that has indexed further, gets that cursor’s ABOVE_LATEST_AVAILABLE (AtCheckpointUpperBound::check_cursor) instead, which it can retry once this server catches up: ListTransactions’ floor_error_or puts the tip refusal of a request with an after cursor before the floor rules.

pub fn check_checkpoint_floor( &self, floor_checkpoint: Option<u64>, upper_bound: &AtCheckpointUpperBound, version_at_floor: impl FnOnce(u64) -> Result<Option<SequenceNumber>>, ) -> Result<()>

Fails with Self::floor_error when a server whose listing floor is floor_checkpoint cannot serve the request’s checkpoint range, as ListTransactions refuses one below its floor. The lowest start_checkpoint it accepts is the checkpoint after the floor, since a range starts above the object’s version at the end of the checkpoint before it. A lower start_checkpoint is served only when an after cursor bounds the listing at or above the floor, as ListTransactions checks the start only after the cursors narrow it: the cursor is at or above version_at_floor(floor_checkpoint), the object’s version at the end of the floor checkpoint, so every version after it was written after the floor, or the object has no version there. A pruned server cannot tell whether an object without one did not exist yet or was removed at or before the floor, so it must also find the object’s history retained from the listing’s lowest version on. An end_checkpoint at or below that lowest start is refused when the listing has no lower bound of its own (neither start_checkpoint nor an after cursor). An empty range lists nothing, whatever the floor. With nothing pruned (floor_checkpoint unset), every range is served.

pub fn nothing_retained(&self) -> ObjectVersionsPlan

The plan of a listing for an object of which a pruning server retains nothing up to the bounding checkpoint: it lists nothing and ends as at the object’s first version, with CHECKPOINT_BOUND.

pub fn checkpoint_window( &self, upper_bound: &AtCheckpointUpperBound, ) -> Result<CheckpointWindow>

The checkpoints the listing covers, against upper_bound’s highest indexed checkpoint, the tip, as ListTransactions bounds them. A descending listing whose end_checkpoint is above the checkpoint after the tip, or whose start_checkpoint is above the tip with end_checkpoint unset, is OUT_OF_RANGE / ABOVE_LATEST_AVAILABLE (bound end_checkpoint or start_checkpoint): it would start above versions this server has not indexed. An ascending listing is never refused for its range: it runs through the tip and ends with LEDGER_TIP.

pub fn plan( &self, window: &CheckpointWindow, upper_bound: &AtCheckpointUpperBound, newest_visible: Option<SequenceNumber>, newest_before_start: Option<SequenceNumber>, ) -> Result<ObjectVersionsPlan>

What the listing reads and how it ends, given newest_visible, the object’s version at the end of CheckpointWindow::bounding_checkpoint, live or not (the newest version written by then), or None if the object did not exist yet, and newest_before_start, its version at the end of CheckpointWindow::below_start (None when that is unset). The checkpoint range lists the versions above newest_before_start up to newest_visible: an object’s versions only increase from checkpoint to checkpoint, so the versions written in a checkpoint range are one version range. The cursors narrow it to the versions between their positions (see ObjectVersionCursor).

A cursor comes from a listing on any server, such as another replica that has indexed further, so it can name a version past this server’s tip: above newest_visible, or at or above [OBJECT_START_VERSION] if it is None. When the window runs to the tip (end_checkpoint unset, or above the checkpoint after the tip), the ledger List APIs’ rules apply to such a cursor:

  • Descending, it is AtCheckpointUpperBound::unindexed_cursor_error, whatever the version range: listing from this server’s view would start below versions it lacks. A before at the version right after newest_visible leaves none between them, so it is served. With newest_visible None, that version is [OBJECT_START_VERSION], the first an object can have, so the boundary at version 0, which a listing of the object that lists nothing mints, is served back as either cursor, unless every cursor of the request comes from a listing bounded above the tip (see Self::check_some_cursor_indexed).
  • Ascending, the listing is served from this server’s view, which holds nothing above the tip. If its window reaches past the tip (see LEDGER_TIP below), an after past the tip lists nothing and ends with LEDGER_TIP, where the client resumes from the cursor it holds, with CURSOR_BOUND if before is at or below the version after after, leaving nothing between them, or with CHECKPOINT_BOUND if end_version is. A window that ends at or below the tip ends by the rules below. A before past the tip leaves the tip as the listing’s end.

A listing with an indexed end_checkpoint stops at it, so every cursor is safe to page from. An empty checkpoint range lists nothing. It ends with CHECKPOINT_BOUND when end_checkpoint - 1 is indexed; ascending above the tip, it ends with LEDGER_TIP, as ListTransactions does.

The listing ends where its range does, at the bound the ledger List APIs would name:

  • The far cursor in listing order ends it with CURSOR_BOUND when the version it names is inside the request’s window (start_version, end_version and the versions written in the checkpoint range) or at its edge: before at or below the window’s end ascending, after at or above its start descending.
  • Otherwise an ascending listing whose window runs to the tip and reaches past the object’s newest version (end_version unset, or above both the version after it and start_version) ends with LEDGER_TIP, since versions written later extend it, even when its after cursor leaves nothing to list: a client following an object’s new versions resumes from its newest version’s cursor.
  • Every other listing ends at the edge of the window the request set, with CHECKPOINT_BOUND, including one whose starting cursor (after ascending, before descending) sits at or past that edge.
Source

pub fn end_cursor( &self, plan: &ObjectVersionsPlan, bounding_checkpoint: u64, ) -> Bytes

The cursor the last frame of a listing that plan plans resumes from, when the listing ends with its planned reason, bounded by bounding_checkpoint: a request in the same order resumes from it.

  • CURSOR_BOUND: the far cursor (before ascending, after descending), unchanged.
  • The starting cursor (after ascending, before descending), unchanged, when it sits at or past the window’s edge, so the listing reached nothing. That includes an ascending after past the tip.
  • Otherwise the window’s edge, which is what the listing reached, as an ObjectVersionCursor::Boundary: ascending, the boundary below the window’s end, above which after lists what the window left; descending, the boundary below the window’s lowest version, at or below which before lists, or above newest_visible when the window lies wholly above it. Versions written later land on the far side of the boundary from what the listing reached, whichever order resumes from it.

pub fn frames( &self, bounding_checkpoint: u64, listed: BoxStream<'static, Result<ObjectVersionItem>>, end: QueryEndReason, end_cursor: impl Future<Output = Bytes> + Send + 'static, ) -> ObjectVersionFrames

The frames of a listing bounded by bounding_checkpoint (see CheckpointWindow::bounding_checkpoint) whose items listed yields in listing order. Each item goes out on its own frame, whose cursor is the item’s: a live version as object, a removal as removal with the fields Self::removal_read_mask selects. The frame with the Self::limitth item ends the stream with ITEM_LIMIT, whatever end says, and listed is not polled again. A listed that ends first is followed by a final frame ending with end, whose cursor end_cursor resolves to once listed has ended (see Self::end_cursor), so a listing with no items still returns a resume cursor. An error listed yields ends the stream with it.
