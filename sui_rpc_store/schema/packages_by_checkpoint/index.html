Module packages_by_checkpoint 

Source
Expand description

(checkpoint, original_package_id, version) → storage_id.

Lists package versions across every package in the order they were published: the key is the 8-byte big-endian publish checkpoint, the 32 raw bytes of the package’s original id, then the 8-byte big-endian version, so key order is checkpoint order. This is the same key layout as the Bigtable packages_by_checkpoint table (sui-kvstore), and backs RpcIndexes::packages_by_checkpoint_iter.

The value is the 32-byte storage id holding that version. Items are identified by (original_id, version), never by storage id alone: system packages are upgraded in place, so every version of a system package shares one storage id.

The CF is a projection of super::package_versions: one row per package_versions row whose publish checkpoint is known. The PackageVersions pipeline writes both CFs in the same commit batch, so they cannot drift. Restore-floor rows (publish checkpoint unset) have no row here. The backfill, which re-indexes checkpoints L through T, re-publishes each version published in that window with its real checkpoint and writes its row here alongside, so once the backfill reaches T, the floor rows left are versions published before the available window. Like package_versions, the CF is never pruned.

A database open (RpcStoreSchema::open) builds this CF from package_versions, writing the row of every version with a known publish checkpoint, until one build completes. That builds the CF for a database created before it existed, and finishes a build a crash interrupted. The build records its completion in super::packages_by_checkpoint_built, and later opens skip it; see RpcStoreSchema::build_packages_by_checkpoint.
